Registration vs reset

  • Registration: reject an email already in use; create a registration challenge. A valid OTP permits account creation.
  • Password reset: delete an old challenge before issuing a new one. Unknown email receives the same accepted response and no email is queued.
  • Each resend replaces the current challenge. A previously queued event becomes stale, and the worker skips it.

What each system is doing

  • Gateway: public request IP token bucket. Identity also rate-limits, so a direct service call does not bypass its own OTP limits.
  • Redis: short-lived HMAC challenge, atomic verification/rate counters, and worker deduplication marker.
  • RabbitMQ: durable, priority-10 queue, maximum 10,000 messages / 10 MiB; reject a new publish when full. Confirm ACK means broker accepted it, not delivered mail.
  • Worker: validates event/current challenge, renders template, retries transient errors; permanent or exhausted errors route to DLQ.

Interview explanation

“Identity stores a five-minute HMAC challenge, publishes a persistent OTP event, and returns accepted only after a broker confirm. A separate notification consumer checks idempotency and that the challenge is still current, then sends the purpose-specific email. Temporary errors retry; terminal errors go to a dead-letter queue. The user later verifies through an atomic compare-and-consume in Redis. Delivery is at least once, so a crash after provider acceptance can cause a duplicate email.”

The event must carry the raw OTP for delivery; HMAC is one-way. Keep RabbitMQ, DLQ, backups, and message logging protected.
